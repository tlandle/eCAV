## Bug 4: WorldFusion gRPC payload too large (~5MB)

Tyler had noted the `pickled_features` gRPC field should be compressed. The proto comment
even said `// Compressed intermediate features` but neither send nor receive had a compression
call. `ecloud_actor_client.py` did raw `msgpack.packb`; `sim_api.py` did raw `msgpack.unpackb`.
For a float16 `spatial_features` BEV tensor the msgpack output is ~5MB, exceeding gRPC's
default 4MB message limit and making WorldFusion distributed non-functional.

Fix: `zlib.compress()` wrapping `msgpack.packb` on send; `zlib.decompress()` before
`msgpack.unpackb` on receive. stdlib, no new dep. Expected ~2-3x compression on float16
activation maps. `[UNPACK FEATURES] ... bytes` log line shows compressed size.

**Result:** Both BM2CP (late fusion) and WorldFusion (intermediate fusion) confirmed working
distributed by end of session.

## Bug 5: Proxy VMs spawning redundant CARLA sensors

Root process proxy VMs were creating 4 CARLA camera actors + lidar per vehicle each tick.
`vehicle_manager.py` was suppressing sensors with flat config keys:
```python
sensing_config['perception']['camera_visualize'] = 0   # never read
sensing_config['perception']['lidar_visualize'] = False  # never read
```
`PerceptionManager` reads nested `config_yaml['camera']['visualize']`, not a flat
top-level key. The overrides were silently ignored.

Fix (`vehicle_manager.py` lines 426-432): switched to nested keys:
```python
sensing_config['perception']['camera']['visualize'] = 0
sensing_config['perception']['lidar']['visualize'] = False
```

## Bug 6: Proxy RSUs same flat-key bug + missing activate=False

`rsu_manager.py` had the same flat-key mismatch. Additionally, `activate` flag was not
suppressed, meaning `PerceptionManager` would still initialize the sensor subsystem.

Fix (`rsu_manager.py`): added `activate=False` and nested camera/lidar suppressors in the
`is_server_proxy` branch.

## Bug 7: Root-process RSU calling LitServe redundantly (3-way contention)

`rsu_manager.py` logic for `is_server_proxy` was:
```python
is_server_proxy = run_distributed and not getattr(cav_world, 'litserve', False)
```
With `-l` (litserve=True), this evaluates `False` → root process RSU used
`WorldFusionPerceptionManager` → independent LitServe call per tick from root process,
competing with vehicle container + RSU container. Root process RSU showed `http=400ms`
(vs vehicle's `~165ms`) because of 3 concurrent GPU jobs.

Fix (`rsu_manager.py` line 88):
```python
is_server_proxy = run_distributed   # matches VehicleManager.use_base_pm semantics
```
With litserve=True, root process proxy RSU now correctly uses base `PerceptionManager`
(no LitServe call). Expected: RSU container drops from ~400ms to ~165ms after restart.

## O5: Edge-coordinated batch inference

Implemented fully. Key design:
- `WorldFusionPerceptionManager.build_batch()`: runs `_build_batch()`, stores in `_pending_batch`; no HTTP
- `WorldFusionPerceptionManager.apply_features(feature_dict_cpu, timing)`: stores features,
  sets `_features_extracted_this_tick = True`, clears pending batch; detect() skips run_step()
- `WorldFusionEdge._merge_wf_batches(batch_list)`: reindexes `voxel_coords[:, 0]` per agent,
  torch.cat all fields, sets `record_len = [1]*N`
- `WorldFusionEdge._run_o5_batch_encoder()`: collect WF-litserve PMs, build all batches,
  merge, one HTTP POST, split `spatial_features[i:i+1]` back to each PM via `apply_features()`
- `_update_agents()`: calls `_run_o5_batch_encoder()` before the per-agent loop (sequential mode only)

**Result in distributed mode**: `batch=1` — expected, because root process has only the
proxy RSU (base PM, not WF PM). The vehicle container holds the real WF PM and calls
LitServe independently. O5 is architecturally a sequential-mode optimization.
