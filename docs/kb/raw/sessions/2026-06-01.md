## Paper 1 — EdgeWarp (SEC '25)

**"Warping the Edge: Enabling Instant Mobility for Stateful Applications over 5G
and Beyond"** — Ahmad et al. (LUMS / KAUST / RIT).

**Problem.** Stateful latency-sensitive edge apps (AR/VR, cloud gaming,
connected/autonomous vehicles; budget <17 ms) suffer downtime during mobility
because app session state must migrate to a new edge site as the user moves.
Generic migration blows the budget: CRIU >140 ms, container >1.2 s, VM >4 s.

**Three bottlenecks they identify.** (1) uncoordinated/reactive app session
migration; (2) slow app session migration; (3) app-agnostic 5G handover — the
control plane has no interface to learn an app's latency needs.

**Design — three modules.**
1. **Target BS prediction.** 8-layer stacked LSTM over Radio Network Information
   (RSRP/RSRQ via MEC RNI APIs) predicts the *target base station* 100 ms ahead
   at 97% accuracy (prior work <85% and only ms ahead). This is the "mobility
   hint" that enables *proactive* migration.
2. **Two-step app state synchronization.** On the mobility hint, `BackgroundSync`
   proactively copies low-update-rate state to the target edge's data store
   (non-blocking). The remaining high-churn dynamic state is moved during the 5G
   handover window via `BlockingSync` (blocking time minimized). Built on
   extended Redis/Memcached with per-key update-rate meta-state.
3. **App-aware control plane.** New AF→AMF/RAN APIs (`Set_Priority` /
   `Revert_Priority`) let latency-sensitive sessions get prioritized
   control-plane signaling; three UE priority classes (LP/MP/HP).

**Results.** 14–15.4× app-downtime reduction (CarMap, EMP); up to 10³× median 5G
handover completion improvement; blocking state migration driven <10 ms.

**Relevance to us — this is the canonical reference for our edge-to-edge handoff.**
- "Predict target BS 100 ms ahead" ↔ predict which locale/edge the vehicle
  enters next — our handoff trigger.
- "Two-step sync (proactive warm + blocking final)" ↔ Tyler's "broadcast state to
  keep neighbor edges warm." EdgeWarp is the principled version of our planned
  `handoff_manager`: `BackgroundSync` warms the target edge; `BlockingSync` is
  the final boundary-crossing transfer.
- Our "naive optimal" handoff (instant, perfect, shared-memory) is the degenerate
  baseline; EdgeWarp characterizes what the realistic *networked* version costs —
  and our Network Model slot is exactly where those costs get injected.
- The low-update vs high-update state split maps onto our edge state: static-ish
  track metadata could be background-synced; live KF positions are the dynamic,
  blocking part.

## Paper 2 — VRF (MobiSys '24)

**"VRF: Vehicle Road-side Point Cloud Fusion"** — Khan, Khalid, Turkar, Dantu,
Ahmad (RIT / Buffalo).

**Problem.** Fuse RSU LiDAR point clouds with a vehicle's point cloud at *both*
low latency (<100 ms, ideally <20 ms) and cm-level accuracy. The motivating
scenarios are occluded intersections — red-light violation, unprotected left —
**our exact blind-intersection research focus.**

**Challenge.** RSU and vehicle clouds come from very different viewpoints → low,
sparse overlap → direct alignment (ICP / feature matching) fails to converge or
is too slow.

**Key insight.** De-couple alignment into *two indirect alignments*: align RSU→3D
map (offline, cached — RSU is stationary) and vehicle→3D map (online via NDT),
instead of aligning RSU↔vehicle directly. Both share large overlap with the dense
3D map, so each alignment is well-conditioned.

**Components.** (1) Offline registration: plane-matching + trajectory-matching to
seed ICP for the RSU's 6-DoF pose in the map. (2) Alignment accuracy forecaster:
uses inter-point density (IPD) to decide *when* an online direct-alignment
refinement will actually help vs. hurt. (3) Fast fusion pipeline: RSU broadcasts a
"diff cloud" (XOR vs a reference frame) cutting bandwidth ~56×; ICP runs against
the cached reference cloud *in parallel* with network transmission; a
motion-vector extrapolation seeds ICP.

**Results.** ~2.4 cm accuracy at <20 ms end-to-end even for 128-beam LiDAR;
order-of-magnitude better than VI-Eye (223 ms) and VIPS. Evaluated on real
testbeds and in CARLA with 6 RSUs.

**Relevance to us.**
- This is the **early / point-cloud fusion** backend Tyler flagged as a future
  slot. It would register into the same `get_fusion()` registry alongside
  `worldfusion` / `late_fusion`.
- Their CARLA setup (6 RSUs, vehicle crossing between RSU coverage zones) is
  directly analogous to our multi-edge locale/handoff scenario: overlapping
  coverage, vehicle traversal across boundaries.
- "Late Fusion with VRF" and "V2V cooperative perception" future-work directions
  overlap our research space.
- Adopting it would inherit two assumptions: an on-board 3D map, and
  offline-cached RSU→map registration.

### Handoff topology decision (jrapp) — peer mesh, not base courier

My first revision proposed the base process as state *courier*
(`Edge_ExportState` on A → `Edge_ImportState` on B). jrapp rejected it: routing
the transfer through the base bakes in a centralized double-hop (A→base→B) and
misplaces the handoff logic. **Correct v1 = Model B realized on `-eo`:** an
edge-owned `handoff_manager` where each edge holds a list of neighbor edges and
communicates with them **directly** (peer mesh). On executing a handoff, the
edge notifies the orchestrator of the event with a TBD payload.

Refined the `-eo` mechanics with three findings (verified against code):

1. **Decision is edge-local.** The ego pose is already serialized into the
   `IntermediateFeaturesBatch` the primary edge receives each tick, so its
   `handoff_manager` runs its own containment check — the base doesn't decide.
2. **Peer channel is the one genuinely new piece of infra.** New
   `Edge_ReceiveHandoff(EdgeState)` RPC; each edge is both server and client to
   its neighbors. The edge already runs `EdgeServer`, so it's additive. Neighbor
   addresses + `locale_bounds` distributed at registration via `EdgeScenarioConfig`.
3. **Orchestrator notification is load-bearing and should piggyback on
   `FusionResult`.** Verified `edge_registration_server.py` does
   `server.stop(grace=2)` after all edges register — there is *no* standing
   edge→orchestrator channel. So the edge adds `handoff_complete{vehicle,
   to_edge, payload}` to the `FusionResult` it already returns to the base. The
   base (= orchestrator process in `-eo`) records the event (metric) *and* flips
   its feature routing to B next tick. One signal, two consumers.

**Why this is safe:** the base routes features to exactly one *primary* edge per
tick, so the base routing table is the single source of truth for "who is
primary" → no split-brain, even though the decision is edge-local. The base
routing table is the consistency backstop.

**Overlap behavior (jrapp):** the hard-cut vs dual-route choice is itself a
**pluggable behavior on the `handoff_manager`** — the modular-slot philosophy one
level down. Build both for v1: **hard-cut first, dual-route second.** A third
behavior (predictive / broadcast-to-all-neighbors) is additive later.
